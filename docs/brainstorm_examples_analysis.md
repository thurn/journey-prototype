# Brainstorm Examples Generation Analysis

This file is the analysis companion to [Brainstorm
Examples](brainstorm_examples.md). For each Dream Journey example, it records
whether the current `journey` command can semantically generate the example, and
— when it cannot — which milestone of [the Brainstorm Generation Gap
Plan](2026-05-08-brainstorm-generation-gap-plan.md) was supposed to enable it,
plus whether the gap is a planning or implementation failure.

Generated by parallel subagents reading code under `src/journey/`.

## Locksmith Counter

- **Verdict:** Generatable but symmetric pattern is coincidence-only
- `service_menu`'s `starter_surgery` family
  (`src/journey/fillers/shapeFills.ts:841-909`) draws from
  `starterSurgeryRewardSlots` (`src/journey/fillers/shared.ts:916-1389`), which
  contains all three operation kinds present in the entry:
  `starter-cleanup-up-to-two` ("Purge up to N chosen Starter cards"),
  `starter-two-chosen-transfiguration` / `starter-random-transfiguration`
  ("Apply {X Transfiguration} to ... Starter cards"), and
  `starter-replacement-draft` ("Replace a chosen Starter card with 1 of 4 X").
- However, `starter_surgery` produces a shuffled `slice(0, 3)` of starter
  rewards (`shapeFills.ts:898-907`); there is no contract enforcing "shared
  starter target, three different card operations" — each slot carries its own
  target/payload independently. The Locksmith Counter pattern (one shared
  target, varied operations) only appears if the shuffle happens to draw exactly
  purge + transfigure + replace-draft. `one_target_many_operations` would be the
  proper symmetric shape, but its `targetClasses` paths only cover `draft_card`,
  `deck_card`, and `dreamsign` (`shapeFills.ts:947-1101`); there is no
  `starter_card` branch.
- This corresponds to Milestone 6 of
  `docs/2026-05-08-brainstorm-generation-gap-plan.md` (Add Starter
  Transformation And Replacement Families), which explicitly names Locksmith
  Counter and required "apply one operation to two chosen starters" plus
  shape-level support. Implementation has delivered the individual
  starter-surgery payloads but not a `one_target_many_operations` starter branch
  nor a symmetric "shared starter target / varied operation" contract — this is
  an *implementation* gap on the symmetric-trio aspect (the planning covered
  it).
- **Suggested resolution:** Extend
  `src/journey/shapes/one_target_many_operations.ts` (and the matching
  `targetClasses` switch in `shapeFills.ts:947-1101`) with a new `starter_card`
  branch that picks a single chosen-starter target via a new
  `chosenStarterTargetEntries` helper, then draws three operations from
  `starterSurgeryRewardSlots` filtered to the
  `cleanup` / `transfiguration` / `replacement-draft` families and emits a
  `shared_starter_target_operations` symmetry contract analogous to the existing
  `shared_target_operations` (line 1032). This converts the current
  coincidence-only trio into a contract-enforced shape and closes the Milestone
  6 implementation gap.

## Forked Remedy

- **Verdict:** Not generatable
- Row 1 ("Purge 2 chosen starter cards") matches the `starter-cleanup-up-to-two`
  reward slot (`src/journey/fillers/shared.ts:1005`). Row 2 ("Gain 1 Nightmare.
  Duplicate a chosen card.") is a *compound option* combining a Bane gain burden
  with a card-duplicate reward, with no shared-prefix structure (only one of the
  two rows carries the burden).
- The reward-slot catalog has no compound `bane_gain + card_duplicate(chosen)`
  slot, and `heterogeneous_pair` (`src/journey/fillers/shapeFills.ts:932`) only
  picks atomic positive reward slots with `effect >= 150`. Bane prefixes are
  only attached via `baneBurdenSlot` in shapes like `one_target_many_operations`
  (line 1080) or `shared_prefix_menu` (line 486), where the prefix must apply to
  all rows or be tied to a different topology.
- This is a planning failure for **Milestone 20** (Compound Payload
  Composition). Milestone 20 covers card/Dreamsign sacrifice + reward bundles
  for `Scissor Saint`/`Molting Archive`, but does not explicitly address
  asymmetric Bane-gain burdens combined with chosen-card duplicate operations in
  a heterogeneous-pair topology. The plan calls for compound bundles, but no
  concrete contract describes a single-row compound where one of two
  heterogeneous options carries a Bane while the other is a pure starter purge.
- **Suggested resolution:** Add a new compound family to
  `compoundPayloadMenuFill` (`src/journey/fillers/shared.ts`) named
  `bane_burden_card_operation` that bundles a `baneBurdenSlot` prefix with a
  chosen-card operation drawn from `cardOperationCatalog.ts` (e.g.
  `chosen-duplicate`, `chosen-purge`), and register it as an eligible single-row
  payload in `heterogeneous_pair`'s atomic-positive pool
  (`shapeFills.ts:932`) so the shape can mix one compound burden+reward row
  with one pure starter-surgery reward row. Gate via a new
  `allowAsymmetricBaneBurden` flag on `heterogeneous_pair` so existing
  symmetric-bane shapes are unaffected. This closes the Milestone 20 planning
  gap by making asymmetric Bane-gain compounds a first-class compound family.

## Veiled Cache

- **Verdict:** Not generatable
- The structure is two parallel root options each with a fixed essence cost and
  a *random pool* reward ("Pay X. Roll for A, B, or C."). No shape produces
  this. `single_random_outcome` only emits one option that pays for a wheel spin
  and one option that does roll-twice-keep-one (`wheelRootOptions` in
  `randomPayloads.ts:712-853`). `random_pool_draws` is a multi-level decision
  tree of "Stop / Pay X to Draw" branches (`treeBuilders.ts:679-752`), not two
  parallel paid wheels with shared cost. `same_cost_different_rewards` shares a
  cost across rows but pulls deterministic rewards from `rewardSlots`, never
  random pool envelopes (`shapeFills.ts:454-484`).
- Gap-plan classification: planning failure. Milestone 17 lists
  wheel/reveal/wager validations (Bounded Wheel, Crooked Coin, Covered Cups) but
  never specifies a "two-row shared-cost paid-wheel" topology, and Milestone
  19's candidate-shapes list does not include this pattern. Veiled Cache itself
  is not referenced anywhere in the gap plan.
- **Suggested resolution:** Introduce a new dream journey shape
  `paired_paid_wheels` (rootOptionCount = 2) under `src/journey/shapes/` and
  register it in `registry.ts`. Each row pairs a shared essence cost slot
  (drawn once and reused across both rows, mirroring the
  `same_cost_different_rewards` shared-cost pattern at `shapeFills.ts:454-484`)
  with a distinct random-pool envelope built from `wheelRootOptions`
  (`single_random_outcome/wheel.ts:23`), each envelope drawing 3 outcomes from
  the random-pool catalog. Emit a `shared_cost_distinct_wheels` symmetry
  contract enforcing that the two envelopes do not overlap in outcome
  categories. Alternatively, extend `same_cost_different_rewards`
  (`shapeFills.ts:454-484`) with a `rewardSource: "wheel_envelope"` branch
  that swaps `rewardSlots` for `wheelRootOptions`-derived random-pool payloads;
  the new shape is cleaner because Veiled Cache's two rows are both wheels
  rather than mixed deterministic/random.

## Lantern Budget

  contract groups them as a coherent resource-only menu, so this is a **planning

  does not call out a "shared resource-domain" symmetry).

  `resourcePayloads.ts:81-90` to include sub-100 entries (e.g. add
  `[80, 90, 100]` as a `low-essence-gain` band) and the max-essence band to
  include `[30, 35, 40]`, then add a `resource_only_trio` symmetry contract
  consumed by `curated_reward_trio` (`shapeFills.ts:911-931`) that filters all
  three rows to entries from `resourceRewardCatalog` and requires three
  distinct resource operation kinds (`gain_essence`, `resource_cap_change`,
  `resource_percentage`) so the resource-domain trio is structural.

## Omen Ledger

- **Verdict:** Not generatable
- The pattern is "shared currency = omens, escalating cost (0/1/2 omens), three
  different reward families (resource gain, card draft, dreamsign choice)." No
  flat-menu shape produces escalating omen costs across rows:
  `flat_escalating_trade` is hardcoded to `Pay N essence. Gain M omens.` only
  (`src/journey/fillers/shapeFills.ts:2045-2082`), `same_cost_different_rewards`
  shares one cost slot across all rows (`shapeFills.ts:454-483`) so all options
  would charge the same cost (e.g. all "Lose 1 omen"), and
  `same_reward_different_costs` shares one reward across rows. Only `costSlots`
  (`src/journey/fillers/shared.ts:2799-2806`) supports a single "Lose 1 omen"
  entry, never escalating omen amounts (1 → 2).
- Decision-tree shapes like `escalating_reward_chain` use escalating *essence*
  costs (`src/journey/fillers/treeBuilders.ts:758-786`) and produce a
  node-chain, not a flat 3-row menu.
- This corresponds to Milestone 19 (`flat_escalating_trade`) and Milestone 10
  (broader resource costs/rewards including "fixed omen cost above 1") in
  `docs/2026-05-08-brainstorm-generation-gap-plan.md`. The plan covers
  escalating trades and varied omen costs, but the implementation of

## One Card, Three Fates

- **Verdict:** Not generatable
- The pattern is three sibling options, each operating on a *different* specific
  named card with a *different* operation kind (purge a named card, duplicate a
  different named card, transfigure a third named card with a specific
  transfiguration). Current `one_target_many_operations` shares one target
  across three operations (`src/journey/shapes/one_target_many_operations.ts`)
  and `one_operation_many_targets` shares one operation across three targets
  (`src/journey/shapes/one_operation_many_targets.ts`); neither produces three
  distinct (target, operation) pairs.
- `curated_reward_trio` could in principle hold three distinct rewards, but
  `rewardSlots` (`src/journey/fillers/shared.ts:2324`) emits at most one
  `named-card-operation:` slot per call (one operation kind per fill, lines
  2579-2640) and has no standalone "Purge {NamedCard}" reward slot — purges of
  specific named cards exist only as burden components inside compound payloads
  (`shared.ts:3205-3260`).
- Closest plan target is Milestone 5 (expand card operation catalog) plus
  Milestone 18 (symmetric compound fill contracts), but neither AC explicitly
  covers a curated trio of three distinct named-target operations across three
  distinct cards. This is a *planning* failure — the gap plan does not call out
  the "three different named targets, three different operations" composition
  pattern.
- **Suggested resolution:** Introduce a new shape
  `heterogeneous_named_card_operations` (file
  `src/journey/shapes/heterogeneous_named_card_operations.ts`, registered in
  `shapes/registry.ts`) with `topology: "direct_menu"`,
  `rootOptionCount: { min: 3, max: 3 }`, validation rules
  `["all_options_distinct_named_targets",
  "all_options_distinct_operation_families"]`. Its fill (new case in
  `shapeFills.ts`) calls `namedDeckCardTargetEntries({ count: 3 })` for three
  distinct named targets, then calls `compatibleCardOperations` three times
  with disjoint `families: ["replacement"]` (purge), `["duplicate"]`, and
  `["transfiguration"]` (one each, `valueBands: ["standard"]`,
  `targetModes: ["exact_named"]`). Emit a new
  `heterogeneous_named_card_operations` symmetry contract recording the three
  (target, operation-family) pairs as varied. Additionally, add a standalone
  `Purge {NamedCard}` reward slot to `rewardSlots`
  (`shared.ts:2311+`) gated on a new `valueBands: ["standard"]`
  `card_purge` family entry in `cardOperationCatalog.ts` that produces
  `Purge {targetCard.name}.` text — currently named-card purges only exist as
  burden components inside compound payloads (`shared.ts:3205-3260`), so
  hoisting one as a first-class reward slot also unlocks reuse by
  `curated_reward_trio`.
